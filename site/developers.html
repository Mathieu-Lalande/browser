Sous le capot de Browser

Le code est lisible sur GitHub : architecture, décisions, tests. Vous trouvez un bug ou une idée ? Ouvrez un ticket ou proposez une demande de fusion, chaque contribution est relue par le mainteneur.

Architecture

  • Ordinateur : Electron 44 (process principal en TypeScript), interface en Svelte 5 (runes), construit avec electron-vite.
  • Téléphone : Expo / React Native dans mobile/, qui partage le cœur src/shared sans le copier.
  • Cœur partagé : src/shared reste pur (ni Electron, ni Node, ni DOM) et testé unitairement : modèles, validation, moteur de synchronisation, i18n.
  • Synchronisation : relais auto-hébergeable dans server/, qui ne voit jamais de donnée en clair (chiffrement de bout en bout).
  • Sécurité : les pages web n'ont ni preload ni accès Node ; chaque message IPC est déclaré dans src/shared/ipc.ts et ses arguments vérifiés dans main.
  • Décisions : chaque choix structurant est un ADR dans docs/DECISIONS.md.

Démarrer

Node 22 et Git suffisent ; le binaire d'Electron est téléchargé à l'installation.

git clone https://github.com/Mathieu-Lalande/browser.git
cd browser
npm install
npm run dev

Installateurs locaux : npm run dist:dir. Détails par système dans docs/INSTALL.md.

Vérifier avant de proposer

La même chaîne tourne en intégration continue sur chaque demande de fusion :

npm run typecheck      # TypeScript + svelte-check, sans avertissement
npm run check:cycles   # aucun cycle d'import dans le process principal
npm run check:i18n     # aucun texte d'interface en dur
npm test               # tests unitaires (Vitest)
npm run build
npx playwright test    # tests de bout en bout dans la vraie application

Selon la partie touchée : cd mobile && npx tsc --noEmit && npx jest, npm run test:server, cd site && npm run build.

Proposer une demande de fusion

  1. Ouvrez d'abord un ticket pour un changement important : on s'accorde sur l'approche avant le code.
  2. Créez une branche dédiée depuis master, gardez la modification ciblée.
  3. Respectez les conventions : code et commentaires en anglais ; tout texte d'interface dans les deux catalogues fr.ts et en.ts ; icônes Lucide ; espacements par les jetons de global.css.
  4. Rien d'écrit sur le disque depuis une fenêtre privée ; aucune donnée envoyée sans action de l'utilisateur.
  5. Ajoutez les tests : unitaires pour la logique pure, Playwright pour le comportement visible.
  6. Décrivez dans la demande ce qui change, les tests exécutés et les limites restantes par système.

Le guide complet est dans CONTRIBUTING.md. Browser est un logiciel propriétaire (licence) : une contribution acceptée est intégrée par le mainteneur.

Signaler une faille

Jamais dans un ticket public : utilisez les avis de sécurité privés de GitHub, comme l'explique SECURITY.md.
